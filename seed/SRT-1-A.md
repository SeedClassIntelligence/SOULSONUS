# SRT-1 · AMENDMENT A — Reconciliation of Build and Reclamation

> **CONSTITUTIONAL TEXT. IMMUTABLE.** Adopted 2026-08-31.
> Amends and refines `SRT-1.md`. Preserved verbatim as received.
>
> **Standing of this amendment:** where Amendment A and SRT-1 §XVII appear to
> conflict on the novice surface, Amendment A §16–17 controls. SRT-1 §XVII
> named the *destination* (a person who has never used a DAW can create).
> Amendment A names the *mechanism* (progressive disclosure inside one surface,
> not a stripped-down second product). The destination is unchanged.

Looking at the current SoulSonus build against the reclaimed architecture and the simplified mock-up, I would not replace this build with the mock-up. The current build contains substantial product architecture that the mock-up deliberately collapsed.

The right move is to reorganize what you already built around the original SoulSonus intelligence model.

My assessment is that the current screen already contains roughly 70–80% of the visible workstation capability we would want on this particular Create screen. What is missing is less about adding dozens more buttons and more about making the intelligence, interpretation, creator intent, and iterative relationship visible.

## 1. What the current build already has—and we should KEEP

Your screenshot is much more sophisticated than an ordinary DAW.

### Creator workflow

You already have the larger production lifecycle:

1. Create → 2. Write & Record → 3. Mix → 4. Master → 5. Release

That is important because SoulSonus isn't merely composition. You're already representing the progression from an idea through a finished asset.

I would absolutely preserve that.

### Creator-origin performance system

This may be the strongest thing visible on the page.

You already have:

* Live Seed & Beatbox Engine
* Record Loop
* Stack Overdub
* transient monitoring
* Oral Beatbox
* Clap/Tap
* Hum/Voice
* MIDI Keys
* performance pads
* real-time event separation
* Pattern Controls
* layers/passes
* BPM/metronome controls

This is directly aligned with the original SoulSonus seed.

In fact, the line:

"Hits split onto isolated channels in real-time as you perform."

is very important.

That's already moving beyond "record my beatboxing" toward:

Human performance → interpretation → musical event separation → structured production material.

Keep it.

## 2. Your structured musical realization is already there

Underneath the performance engine you've got the translated result:

Kick (Thump) / Snare (Clap/Pop) / Hi-Hat (Tss) / 808/Sub Bass / Lead Synth/Keys / Strings Ensemble / Lead Vocal Track / Harmony Stems

And those events exist across a bar-based editable timeline.

That is essentially the downstream side of:

expression → interpretation → structured music.

Your current build therefore already demonstrates part of the invention much better than a generic waveform DAW would.

The mock-up kept this concept, but actually removed much of your implementation depth.

## 3. A lot of your surrounding SoulSonus ecosystem disappeared from my mock-up

This is the biggest difference.

Your current build has an entire Studio Utilities & Workstations architecture:

Piano • Instrument • Signature • Sourcing • Collab • Native Brain • Workstation • Songwriting • MIDI Hardware • Inspector • Calibration • Radial Radar • Import Audio • Pipeline

I reduced almost all of that into a left navigation rail.

That simplification helped communicate the concept, but it is too reductive for the actual SoulSonus product.

These aren't random buttons. Several appear to represent distinct production subsystems.

For example:

**Signature** — This potentially connects to the creator's musical identity, SeedSignature, provenance, preferences, authorship, and recurring creative characteristics.

**Sourcing** — Potentially handles sounds, samples, instruments, models, external resources, or musical assets.

**Native Brain** — Potentially represents SoulSonus's embedded intelligence layer.

**Calibration** — Potentially handles audio/input/device/environment calibration.

**Radial Radar** — Potentially provides analysis or awareness across the session.

**Pipeline** — Potentially exposes production flow or processing state.

**Inspector** — Essential for professional-level parameter editing.

**MIDI Hardware** — Important because SoulSonus shouldn't become voice-only.

Your original philosophy is:

natural human expression can be an input modality

—not:

"traditional musical interfaces disappear."

So MIDI keyboards, hardware controllers, microphones, audio files, instruments and conventional DAW interaction all remain legitimate first-class inputs.

## 4. You also already have sections/arrangement intelligence

This part should remain.

I see:

ALL SONG

and defined sections such as:

* Intro Beat
* Verse Pocket
* Chorus Lead Hook
* Outro Resolving Tail

plus:

* Edit Sections
* bar selection
* 4/8/16/32/64-bar controls
* section navigation

That's important.

It gives SoulSonus an understanding above the level of individual notes.

The intelligence eventually needs to understand:

"Make the chorus bigger."

not merely:

"Change events at bars 17–24."

Those section objects provide the semantic structure necessary for conversational production.

## 5. Your editing tools are also stronger than what I showed

You've already got:

Select • Draw • Stretch • Split • Erase • Notes • Add Track • AI Realization

That is exactly the correct relationship between conventional DAW manipulation and AI-assisted creation.

The user can either:

manually manipulate music

or

ask SoulSonus to realize an intention.

That duality should stay.

## 6. There are important governance/provenance concepts here too

At the bottom I see:

SeedSignature: READY TO SIGN
Rights: 100% SoulSonus Master Creator
Collab: 1 ACTIVE

Those are not decorative.

They're pointing toward a much larger creator-rights architecture involving:

creation → provenance → contribution → ownership → collaboration → release.

That becomes particularly important once AI generation and human collaboration coexist.

My simplified mock-up included provenance conceptually, but your current implementation exposes it more explicitly.

Keep it.

## 7. So what did my mock-up actually improve?

This is where the two designs need to merge.

Your existing screen is functionally richer.

My mock-up was cognitively clearer.

Your screen tells me:

"Here are the capabilities of SoulSonus."

The reclaimed mock-up tries to tell me:

"Here is what SoulSonus understands about what I am trying to create."

That second piece is what I believe your current interface still needs.

## 8. The largest missing layer: Creative Intent

This is probably the single most important addition.

Your current screen shows the musical events beautifully.

But where does SoulSonus show:

What am I trying to make?
What did SoulSonus hear me express?
What does it believe should be preserved?
What is allowed to change?
What emotion did it interpret?
What musical role did it assign to my vocal imitation?
How confident is it?

That is why I put the Creative Intent Model into the mock-up.

For example:

```
CREATIVE INTENT
Emotional trajectory: Intimate → Resolute
Genre grammar: Neo-Soul / Gospel
Groove: Behind the beat / human
Preserve: Lead melody + vocal cadence
Transform: Harmony, instrumentation, texture
Energy: Controlled lift
Arrangement: Sparse verse → expansive hook
```

That shouldn't necessarily consume permanent screen real estate.

It could be an intelligent collapsible panel.

But SoulSonus needs somewhere to expose its understanding.

Otherwise the intelligence remains invisible.

## 9. The second major missing layer: the interpretation step

This is even more fundamental.

Suppose you perform:

"dum… dum-dum… DA-dum…"

SoulSonus shouldn't immediately pretend it knows what that means.

It might infer:

```
Possible musical roles
Bass line — 82%
Low synth — 68%
Kick/bass hybrid — 41%
```

Then:

Preserve my timing. Make that an electric bass.

SoulSonus creates the bass representation.

That gives us:

PERFORMANCE → INTERPRETATION → CREATIVE INTENT → MUSICAL REALIZATION

Your current screen does Performance → Realization extremely well visually.

We need to expose the middle.

That middle is where a significant portion of the SoulSonus intelligence actually lives.

## 10. Vocal mimicry needs to become more prominent

Your current interface strongly emphasizes beatboxing.

That's good—but the reclaimed SoulSonus seed is broader.

The Live Seed & Beatbox Engine should probably mature into something closer to:

**Live Expression Engine**

with modalities:

Beatbox | Hum | Sing | Mimic | Clap/Tap | Speak | MIDI

Then context changes depending on what you're doing.

For Beatbox: Thump → Kick / Pff → Snare / Tss → Hi-hat

For Mimic: "Bummm-bum-ba-bumm" / Possible role: Bass / Pitch contour detected / Groove detected / Articulation: muted/plucked / Realize as: Electric Bass / Synth Bass / Upright / 808

For Hum: Melody detected / D minor / 7-note phrase / Preserve expressive timing? / Quantize? / Harmonize? / Convert to instrument?

That's much closer to the complete invention.

## 11. Vocal-to-Lyric still needs a dedicated experience

I don't see the reclaimed Vocal-to-Lyric intelligence represented clearly on this screen.

That should become a proper SoulSonus workstation.

Not simply transcription.

It should distinguish:

Words recognized / from phonetic fragments / from melodic syllable positions / from semantic intent.

For example, vocal seed:

"I been wai— / something calling me home…"

SoulSonus could understand:

Theme: return/redemption
Cadence: preserved
Syllable pattern: 4 / 6 / 5
Rhyme position: bar 4
Melody: locked

Then propose lyric alternatives without destroying the performed cadence.

That is distinctly SoulSonus.

## 12. The Studio Intelligence needs to become persistent

You already have the orange ✣ STUDIO INTELLIGENCE. Excellent.

I would build on that rather than adding another unrelated AI button.

When opened, Studio Intelligence should become the session-aware co-producer/engineer from the mock-up.

It should know:

* selected section
* selected track
* all tracks
* lyrics
* performance history
* current mix
* instrumentation
* effects
* routing
* BPM/key
* creator intent
* SeedSignature
* collaborators
* revisions
* provenance
* AI-generated material
* human-generated material
* what is locked
* what can change.

Then you can simply say:

"I like everything except the bass."
or "Make the second chorus feel like I've finally made it through something."
or "Don't touch my vocal."
or "Why does this sound muddy?"

And Studio Intelligence understands the actual project, not just the sentence.

That is a major distinction.

## 13. We need a visible non-destructive ChangeSet system

This is one area where I think the mock-up definitely improves the current screen.

Studio Intelligence shouldn't just execute invisible AI actions.

It should say:

```
PROPOSED CHANGE
Harmony Stem
• widen voicing
• raise upper harmony +3 semitones
• reduce density in verse
• introduce response vocal in chorus

Will NOT change
✓ Lead vocal
✓ Melody
✓ Beatbox timing
✓ Lyrics
```

Then: Preview | Apply | Alternative | Reject

Applying creates: Revision 19 — rather than overwriting Revision 18.

This makes AI trustworthy and makes the production workflow professionally usable.

## 14. Revision history needs to become more than Undo

Your current build has Undo Last Pass and project version information.

We should expand that into: **Revision Tree / Creative History**

```
Original Seed
   │
   ├── Beatbox Interpretation 01
   │
   ├── Bass Realization 03
   │
   └── Arrangement v4
           │
           ├── Dark Version
           │
           └── Hopeful Version
                   │
                   └── Current Master
```

Then a creator can say:

"Give me the drums from version 12 with the bass from version 16."

That is much more powerful than conventional undo.

## 15. Emotion needs a real control/analysis system

The screenshot doesn't yet communicate the emotionally intelligent composition concept strongly enough.

We don't need an enormous "emotion dashboard."

But SoulSonus should understand something like:

Valence / Arousal / Tension / Intimacy / Confidence / Darkness–Brightness / Movement

and translate those into musical consequences.

Then Studio Intelligence can explain:

"Your performance became more intense in the last phrase. I preserved that lift by widening the harmony and increasing rhythmic density rather than increasing tempo."

That's emotionally intelligent composition.

Not: Sad = minor key.

## 16. The professional DAW controls should NOT disappear

This is where I would explicitly reject over-simplification.

We should not turn SoulSonus into six giant buttons:

Hum / Sing / Beatbox / Generate / Remix / Export

That would destroy much of what you've already built.

SoulSonus has evolved beyond that.

The professional user still needs:

tracks, clips, MIDI, mixer, sends, buses, effects, plugins, automation, sections, takes, stems, routing, hardware, quantization, timing, gain staging, mastering and export.

**The innovation is that a person doesn't have to know all of those things to create with them.**

That's fundamentally different.

## 17. The interface problem is therefore progressive disclosure

Your screenshot is not fundamentally wrong.

It is too simultaneous.

That's different.

At the moment I see nearly every subsystem saying "I'm available!" at the same time.

We should instead establish hierarchy.

**Level 1 — Creative context.** Always visible: Project | Transport | Create/Write/Mix/Master/Release | Studio Intelligence

**Level 2 — Current creative activity.** If you're beatboxing: Expression Engine + Beatbox controls. If you're writing: Lyrics + melody + structure. If you're mixing: Mixer + tracks + Studio Engineer. If you're mastering: Master chain + loudness + delivery.

**Level 3 — Production workspace.** Timeline / tracks / clips / sections.

**Level 4 — Specialist utilities.** Piano, Instrument, Sourcing, Calibration, MIDI Hardware, Inspector, Radar, etc. Available instantly—but not permanently demanding attention.

That preserves everything while making SoulSonus feel substantially calmer.

The resulting architecture would look conceptually like this:

PROJECT     TRANSPORT        STUDIO INTELLIGENCE      EXPORT

CREATE     WRITE & RECORD     MIX     MASTER     RELEASE

─────────────────────────────────────────────────────────

## What I would NOT add yet

I would resist adding more miscellaneous workstations until we've reconciled the ones already present.

You already have plenty of tools.

The missing architecture is predominantly the connective intelligence:

Human Expression → Interpretation → Intent → Musical Representation → Realization → Project State → Studio Intelligence → Proposed Change → Creator Approval → Revision.

Your existing screen strongly represents Expression, Musical Representation, Realization and Project State.

The mock-up introduced Intent, Studio Intelligence, ChangeSets and Revision reasoning.

Those are the two halves.

## So how much did we keep?

From the original SoulSonus concept, the current build has retained a surprising amount—especially creator-origin input, beatboxing, musical realization, structured tracks, arrangement, utilities, rights, collaboration, and the professional workstation concept.

From the current application's visible functionality, my mock-up probably represented only about 45–55% because I intentionally stripped away most specialist workstations and production controls to expose the cognitive model.

So I would not rebuild SoulSonus around my simplified mock-up.

I would use the current build as the functional foundation, and use the reclaimed mock-up as the interaction/intelligence architecture that organizes it.

That gives us the product we've actually been describing all along:

**a full professional music-production environment where conventional tools remain available, but the primary abstraction above them is the creator's musical expression and intention—not the creator's technical knowledge of the software.**

And I think that distinction tells us exactly what the next UI iteration should be.
