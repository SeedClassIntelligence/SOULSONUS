The ACE Seam

What stands between the capability registry and a working ACE runtime inside SoulSonus — read from the pinned fork rather than recalled, with every answer marked by where its evidence came from.

Fork seedclassintelligence/ace-step-1.5 @ 6d467e4 SoulSonus main @ 028e34f 19 Aug 2026

The finding in one paragraph

ACE is not integrated. src/lib/capabilityRegistry.ts holds seven manifest records naming repository URLs, a frozen commit, a checkpoint and source-file paths — and nothing in the app calls any of it. There is no client, no endpoint invocation, no audio return path. One entry is CAP-003_REST_API pointing at acestep/server/api.py; no client for it exists.

The good news is larger than the gap. The fork ships a complete asynchronous HTTP service, the checkpoint already named in our registry is the one variant that supports the surgical multi-track tasks, and — the detail that matters most for a DAW — ACE locks output duration to the source audio for cover, repaint, lego and extract. A generated part comes back the same length as the context you sent it. That is timeline alignment for free.

What is genuinely missing on our side is one structural type: a first-class audio clip. Everything else needed for the first vertical slice — candidate governance, audition, commit, reject, lineage, undo — already exists in some form.

The eleven answers

01

Which checkpoints are present or obtainable

From the fork

No weights ship in the repository — there is no checkpoints/ directory and nothing under LFS. Models are fetched at first run through huggingface_hub.snapshot_download, with ModelScope as an alternate source, into a directory set by ACESTEP_CHECKPOINTS_DIR.

Obtainable DiT: acestep-v15-base · -sft · -turbo (2B) — acestep-v15-xl-base · -xl-sft · -xl-turbo (4B)
Obtainable LM: acestep-5Hz-lm-0.6B · -1.7B · -4B
Downloader: acestep/api/model_download.py
Our registry names: acestep-v15-xl-base — a real, published checkpoint

Whether that checkpoint is already on any machine of ours is not answerable from source. Needs a machine

02

Which task types our checkpoint supports

From the fork

The model zoo table in README.md is explicit, and it vindicates the choice already recorded in the registry: acestep-v15-xl-base is the only XL variant that exposes Extract, Lego and Complete. The SFT and Turbo variants stop at text2music, cover and repaint.

xl-base  text2music ✓  cover ✓  repaint ✓  extract ✓  lego ✓  complete ✓  · 50 steps · CFG ✓
xl-sft   text2music ✓  cover ✓  repaint ✓  extract ✗  lego ✗  complete ✗
xl-turbo text2music ✓  cover ✓  repaint ✓  extract ✗  lego ✗  complete ✗ · 8 steps · no CFG

The three tasks only base exposes are precisely the three that fit a multi-track studio. Whoever pinned that checkpoint chose correctly.

Which Python entry point to invoke

From the fork

One function, two long-lived handlers. The handlers hold the loaded models; the function is stateless per call.

from acestep.handler import AceStepHandler
from acestep.llm_inference import LLMHandler
from acestep.inference import GenerationParams, GenerationConfig, generate_music

generate_music(dit_handler, llm_handler, params, config, save_dir=None, progress=None) -> GenerationResult

Defined at acestep/inference.py:503. Helper functions understand_music, create_sample and format_sample live alongside it for analysis and prompt shaping.

04

Existing REST server, or our own wrapper

From the fork

A full asynchronous job service already exists. Run it; do not rebuild it. Our wrapper's job is translation and governance, not inference orchestration.

POST /release_task  submit, returns task_id and queue position
POST /query_result  batch poll — status 0 running · 1 succeeded · 2 failed
GET  /v1/audio?path=  download the rendered file
GET  /v1/models  list loaded checkpoints
POST /format_input  LM caption and lyric shaping

Launch: ./run_api_server.sh · default port 8001 · optional ACESTEP_API_KEY
Accepts: JSON with server-side paths, or multipart upload of src_audio / reference_audio

Multipart upload is the important half for us: SoulSonus holds Blobs in a browser, not files on the inference host, so we post the bytes and never think about shared filesystems.

One trap, and we have hit its twin before. CORS in acestep/api/route_setup.py:62 allows only localhost and 127.0.0.1 origins. A browser on any other host is refused before the model is ever consulted — exactly how the Demucs client failed. Either the service runs beside the app, or our wrapper is the only thing the browser talks to.

05

What inputs each task requires

From the fork

Four of the six need nothing more than source audio and an instruction string. That is a low bar for a first integration.

text2music  caption · lyrics · optional bpm, key_scale, time_signature, duration (10–600 s)
cover       src_audio · caption · audio_cover_strength (0.0–1.0; 0.2 ≈ style transfer)
repaint     src_audio · repainting_start · repainting_end (−1 = to end) · caption
lego        src_audio · instruction "Generate the {TRACK} track based on the audio context:" · caption
extract     src_audio · instruction "Extract the {TRACK} track from the audio:"
complete    src_audio · instruction "Complete the input track with drums, bass, guitar:" · caption

Track vocabulary: vocals · backing_vocals · drums · bass · guitar · keyboard · percussion · strings · synth · fx · brass · woodwinds

That vocabulary is worth noting against our own ExtractionTargetClass union, which now carries the same names plus music and keys. The overlap is close enough to map directly, and the two extras are ours, not ACE's.

06

What each task returns

From the fork

Audio plus the metadata the model actually resolved — which matters, because on some tasks the model overrides what you asked for.

In-process: GenerationResult { audios[], status_message, extra_outputs, success, error }
Over HTTP: result[] { file, status, metas{bpm, duration, keyscale, timesignature, genres},
                   generation_info, seed_value, lm_model, dit_model }
Formats: flac · wav · wav32 · mp3 · opus · aac  — take flac or wav32
Batch: up to 8 renders per request; every one is a separate candidate

The alignment gift. At acestep/inference.py:819, duration is forced to the source length for cover, repaint, lego and extract — whatever the caller passed is discarded. Send four bars of context, get four bars back. The returned audio drops onto the timeline at a known start with a known length, with no stretching and no guesswork.

The exception is complete, which is not in that list. Treat its output as a clip of unknown length until measured.

07

Runtime requirements

From the fork

The tasks we want are the expensive ones. This is the line item that decides whether ACE is a local feature or a hosted service.

≥24 GB  xl-base for extract / lego / complete + acestep-5Hz-lm-4B — everything resident
20–24 GB  XL turbo/sft, LM 1.7B, vLLM backend
≥12 GB  XL runs with CPU offload and quantization
≤6 GB  2B turbo only, LM disabled

XL weights: ~9 GB bf16 (vs ~4.7 GB for the 2B family) · 50 inference steps, not 8

Corrected after review. An earlier version of this line read "a creator's laptop will not run the surgical tasks", which the source does not support. What the table actually says is that the configuration we want is heavy — everything resident wants ≥24 GB, and XL runs at ≥12 GB with offload and quantization at reduced capability. That is an operational fact about today's hardware and today's checkpoints, not a permanent one.

So: V1 assumes hosted inference, and the wrapper is written as if the model is on another machine, because in V1 it is. But the architecture should not be frozen around "local is impossible". The seam to hold open is a provider interface — E05RealizationProvider, with HostedAceStepProvider today and room for LocalAceStepProvider and SoulSonusNativeProvider — so that quantization, distillation or a native renderer changes an implementation rather than the design.

08

Where the 5Hz LM participates

From the fork

The split is hard-coded by task type, not configurable, and it is in our favour.

acestep/inference.py:612
skip_lm_tasks = {"cover", "cover-nofsq", "repaint", "extract"}

LM bypassed entirely: cover · repaint · extract — thinking=true has no effect
LM participates: text2music · lego · complete

Two distinct jobs when it does run:
  Phase 1a — fill missing metadata: bpm, key_scale, time_signature, duration, caption, language
  Phase 1b — generate audio_code_string, the 5 Hz semantic plan, only when thinking=true

The code comment on the extract case is instructive: LM-generated captions conflict with the extract instruction and make the model reconstruct its input instead of isolating a stem. On these tasks the planner is not merely unnecessary — it is harmful, and they excluded it for that reason.

09

The seam for SoulSonusMusicPlanner

From the fork

There is nothing to carve out. The seam is already a parameter boundary, and it is narrow.

Everything the LM produces is a plain field on params:
  bpm · keyscale · timesignature · duration · caption · vocal_language · audio_code_string

To become the planner, supply them and switch it off:
  thinking=false · use_cot_caption=false · use_cot_language=false · use_cot_metas=false

Guard at inference.py:634: use_lm = (thinking or need_lm_for_cot) and initialized and not skip_lm

So the replacement lands in three tiers, and only the third is real work:

  • Already ours. Repaint, extract and cover take no planner at all. Choosing the region, the stem and the preservation contract is the planning, and SoulSonus does it.
  • Ours by simply filling fields. Lego and complete need bpm, key, time signature and a caption. We hold all four as session state — the session is a better source than a model guessing from audio.
  • Genuinely open. Only audio_code_string, the 5 Hz semantic plan, has no equivalent on our side. That single field is the whole substance of a native planner, and it can be deferred indefinitely: leave thinking=false and the DiT runs without it.
10

What DAW state is missing

From our code

Less than expected. The governance shell is built; the timeline representation is not.

Missing outright
  AudioClip — no equivalent exists anywhere in src/types/daw.ts
  A track can hold NoteEvents. It cannot hold audio at a position.

Exists but is the wrong shape
  AudioAsset — a sound-library record (SoundAsset + blob), not an immutable timeline asset
  no sampleRate, channels, hash, or parentAssetIds

Exists and is usable now
  GenerationCandidate — candidateId, audioAssetId, backend, seed, preservation scores,
  violations, creatorDecision, governanceState, commit transaction, idempotency key
  RealizationCandidateDrawer — mounted, with audition / commit / reject wired
  AssetLineageRecord — written on commit
  History — one stack over tracks and arrangement, with labelled entries

The candidate that drawer receives today is fabricated: src/App.tsx:139 builds it from an asset id ending _demo and four literal preservation scores, and the lineage record it commits carries sourceAssetId: 'ast_src_orig'. No audio passes through any of it. But the shape is right, the lifecycle is right, and it is mounted — the work is filling it with a real render, not designing it.

Your proposed AudioClip and AudioAsset pair is the correct model and I would not change the fields. Two notes from our side: startTick and durationTicks should match the existing NoteEvent tick domain (480 PPQ) so clips and notes share one timebase; and clip audio needs the same treatment take audio just received — the blob persisted in the project snapshot, with the object URL rebuilt on load, because a URL does not survive a reload.

11

The smallest honest vertical slice

From our code

Not the slice you proposed — a smaller one. extract beats lego as the first proof, for three reasons that all reduce what has to be true on the first attempt.

  • It needs no caption, no lyrics, no planner — one instruction string and a file. The LM never runs, so the whole LM configuration surface stays out of the first test.
  • Its output is duration-locked to the input, so clip placement is arithmetic, not judgement.
  • It is verifiable by measurement: extract the vocals from a mix we made, and the result must correlate with the vocal we recorded. A generated part can only be judged by ear; an extracted one can be checked.

That last point is what makes it an honest first proof rather than a demo.

Slice one, step by step

Every step ends in something observable. Nothing here requires a new room, a new workspace, or a redesign of the DAW.

  1. Bounce the source.

    Render the current project through the existing master bounce and encode it — this already works and needs no change. That file is the src_audio.

  2. Post the job.

    A thin client posts multipart to /release_task with task_type=extract, the bounced file, and instruction="Extract the vocals track from the audio:", then polls /query_result until status 1 or 2. A failure surfaces as a failure — no placeholder candidate.

  3. Fetch and register the asset.

    Download from /v1/audio, hash the bytes, and store an immutable AudioAsset carrying sampleRate, channels, duration, hash, and the source asset id it came from.

  4. Place it as a clip.

    An AudioClip on a new channel at startTick 0, its durationTicks derived from the measured length — which, on extract, must equal the source. If it does not, that is a bug worth catching on day one.

  5. Run it through governance.

    Hand the drawer a real GenerationCandidate pointing at that asset. Audition plays the clip. Reject discards asset and clip. Commit writes a lineage record naming the true source asset — not ast_src_orig.

  6. Prove the invariants.

    One undo removes clip, asset and candidate together. The project reloads with the clip intact and playable. The provenance record hashes the bytes we actually received.

What this changes about sequencing

Your priority order holds, with one adjustment I would argue for.

The audio clip is not step two — it is step one, and it is worth building for its own sake before ACE is in the picture at all. Recorded takes, imported files and separated stems all currently have nowhere to live on the timeline; that is a gap in the studio whether or not a model ever fills it. Building AudioClip against material we already have — a take we recorded ourselves — proves the type without a GPU in the loop, and turns the ACE slice into plumbing rather than plumbing plus a new core abstraction.

The other adjustment is smaller: the planner replacement can be split. Repaint, extract and cover need no planner today, so they can ship while audio_code_string remains ACE's. There is no need to treat the planner as one gate in front of all six tasks.

What could not be settled from source

  • Whether the checkpoint is in hand. Nothing in the repository says what any of our machines already hold.
  • Real latency per task. 50 steps at 4B on a 24 GB card is a measurement, not a number to be read. It decides whether extract is interactive or a background job — and that decides the UI.
  • Extract quality against our material. Isolating a stem from a dense mix is a different problem from isolating one from four sparse beatbox channels. The docs cannot answer it; a test can.
  • Whether complete returns the source length. It is absent from the duration-locking rule; that is evidence, not proof.

All four are one afternoon on a GPU box, and all four should be answered before any of this is scheduled.
